# 代码评审（Code Review）

CI 只证明"机器能跑"，评审证明"该做的事做了"。双轴缺一不可。

## 标准轴（对照 docs/standards/）

- **code-style.md**：强类型完备？命名正确？定义顺序（gdlint 已管）？
  逻辑/表现分离？autoload 干净（无 class_name）？
- **testing.md**：正常路径 + 边界/错误分支都测了？错误分支显式消费了？
  测试消息可读？
- **scene-asset.md**：新场景 UniqueName 到位？.import/.uid 一并提交？
  无固定像素坐标布局？
- **ADR 合规**：改动是否与既有 ADR 冲突？冲突则必须有新 ADR 声明取代关系。

## 需求轴（对照 Issue/验收标准）

- 逐条核对验收标准 → 每条标：已实现+有测试 / 已实现+试玩验收 / 未实现（说明）
- 有没有**夹带**（PR 里混入无关改动）？有则要求拆分。
- 有没有**遗漏的联动**：改了机制没改 GDD？改了 schema 没写迁移？
  加了数值没加模拟验证？

## 评审输出格式

```markdown
## 标准轴
- [x/问题] 具体位置 + 违反条目 + 建议修法

## 需求轴
| 验收标准 | 状态 | 证据 |
| --- | --- | --- |

## 结论
- approve / request changes / comment
- 必改项（阻塞合并） vs 建议项（可后续）
```

## Agent 自查用法

Agent 提 PR 前以本 skill 自查一轮，是"写完自己评审"义务的落地形式：
1. git diff 自读一遍（以评审者心态，不是作者心态）
2. 双轴逐项过
3. 证据贴进 PR 自检清单

## 红线

- 禁止"CI 绿了就直接合"（CI 不覆盖需求轴）
- 禁止评审自己提出的需求时跳过需求轴（自嗨检查最容易被跳过）
