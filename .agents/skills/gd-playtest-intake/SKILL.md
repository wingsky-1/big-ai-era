# 试玩反馈摄入（Playtest Intake）

人类试玩后的反馈是项目最贵的数据源。你的任务：把"感觉跳跃太飘了"
这类主观感受，翻译成**可验证、可实施、可关闭**的工程任务。

## 分诊协议

拿到反馈先归类（可叠加）：

| 类别 | 信号词 | 去向 |
| :--- | :--- | :--- |
| Bug | "卡住/穿墙/黑屏/报错" | gd-lead-programmer，先复现再修 |
| 手感 | "太飘/太硬/不跟手" | 拆参数 → gd-balance-designer 调表 |
| 节奏/难度 | "太难了/无聊/重复" | gd-lead-designer 改机制或曲线 |
| 表达 | "看不懂/不知道要去哪" | gd-ui-ux-designer + gd-narrative-designer |
| 灵感 | "如果能…就好了" | gd-producer 切片 → gd-lead-designer 立项 |

## 还原协议（Bug 类必走）

1. **先复现**：按 Issue 描述在本地/构建版复现；复现失败 → 补信息评论，
   不得猜测性修复。
2. **最小复现**：定位到最小触发条件（输入序列、数据状态）。
3. **回归测试**：修复后必须补一个能抓住此 Bug 的测试（GUT），
   Bug 描述转成测试名（如 `test_dashing_into_wall_does_not_clip`）。
4. **归档**：反馈要点与处理结果归档到 `docs/playtest/`（documentation.md 格式）。

## 转化协议（体验类）

- 主观感受 → 可量化代理指标：
  "太飘" → "落地缓冲时间 > X 秒"（X 由数值表确认，调参后人类复测）
- 无法量化的 → 标注"试玩主观验收"，在 PR 的试玩验收指引中写清预期变化。
- 任何反馈必须闭环：Issue 回复处理方案 + 预期出现的版本 + 归档链接。

## 红线

- 禁止把人类反馈直接转成代码改动而不做分诊（很多"要功能"其实是"要体验"）
- 禁止关闭反馈 Issue 时无归档、无方案说明
