# 文档体系规范

> 文档是"活文档"：与代码同仓库、同 PR、同生命周期。
> 原则：**改了玩法必须同步 GDD；改了架构必须补 ADR**——由 PR 模板自检清单强制。

## 目录结构

```text
docs/
├── gdd/          # 游戏设计文档（活文档，持续演进）
├── adr/          # 架构决策记录（只追加，不修改历史）
├── playtest/     # 试玩反馈归档（按日期命名）
└── standards/    # 工程规范（本目录）
```

## GDD（游戏设计文档）

- 入口：`docs/gdd/gdd.md`，章节结构：
  **愿景一句话 → 核心循环（Core Loop）→ 机制清单 → 操作/输入映射 → 成长/经济 → 未决问题**。
- 每个机制一个章节，必须包含：目的（制造什么体验）、规则（可验证的表述）、数值引用
  （指向 `src/data/*.json` 的键名，不复制数值本体）。
- 状态标记：`[已实现]` `[开发中]` `[提案]` `[废弃]`，随 PR 更新。
- Agent 在实现任何机制前**先读对应章节**；人类的新想法先进 GDD 再进 Issue。

## ADR（架构决策记录）

- 命名：`docs/adr/NNNN-短标题.md`（四位序号，只增不改）。
- 模板：

```markdown
# NNNN. 标题

日期 / 状态（proposed | accepted | superseded by NNNN）

## 背景（Context）
遇到了什么问题、什么约束。

## 决策（Decision）
选了什么。

## 备选方案（Alternatives）
考虑过什么、为什么放弃。

## 后果（Consequences）
正向收益 + 需要接受的代价。
```

- 触发条件：更换引擎版本/插件、目录结构调整、新增 autoload、通信模式变更、
  存档 schema 破坏性变更。

## 试玩反馈归档

- 文件名：`docs/playtest/YYYY-MM-DD-<版本>.md`。
- 内容：试玩环境 → 亮点 → 槽点 → 疑似 Bug → **行动项**（转 Issue 的直接列出 Issue 链接）。
- 归档来自 Issue（playtest-feedback 模板）的处理结果；Issue 关闭时必须归档或注明去向。

## 文档红线

- 代码与文档在同一 PR 中变更，禁止"回头补文档"成为常态。
- 文档之间引用用相对路径；禁止复制粘贴内容（单一真源，互相引用）。
