# 试玩脚本真源（scripts.md · v0.1.5 的 `[P]` 验收凭据）

> **性质**：流程资产（`docs/playtest/`），非设计稿、非 issue、非测试代码。
> **真源关系**：每条脚本从 `docs/discussion/2026-09-08-v1-requirements.md`（下称"需求文档"）各模块 `[P]` 验收点的三段式（**步骤脚本 / 预期感受 / 代理指标**）逐条提取，并对照 v0.1.5 各 issue 正文的 `[P]` 原文；**不发明任何玩法数值**。凡出现数值，一律引用 `src/data/*.json` 的键名与值（核对清单见附录 B）。
> **覆盖范围**：v0.1.5 milestone 全部 **13 张单**（#67、#71–#82）的 `[P]` 验收锚点，一个不少（自检表见附录 A）。
> **状态**：`[开发中]`——脚本的**可执行性受当前构建能力边界约束**（§0.5），缺口项如实标注、未自行放宽；需主程序席裁决的项集中列在附录 C。
> **维护**：改脚本 = 改本文件 + 在对应 issue 评论留痕；归档规则见 `docs/standards/documentation.md` §试玩反馈归档、`docs/playtest/README.md`。

## 0. 卷首

### 0.1 目的

`[P]` 是**真人试玩验收**的唯一凭据（`docs/standards/issue-spec.md` §6："主观项禁止伪装成 `[T]`；`[P]` 项留给真人试玩勾选，禁止 agent 代跑冒充完成"）。本文件把"13 张单里那些只有人能判的验收点"翻译成**可照做、可复现、可判定**的脚本，使：

1. 试玩者不需要读设计文档即可执行；
2. 同一条 `[P]` 在不同人手里判出同一结论（代理指标带数字/明确动作）；
3. 不通过时有明确的归因方向与建议 issue，而不是"感觉不好"。

### 0.2 适用范围

| 项 | 内容 |
| :--- | :--- |
| 版本 | **v0.1.5**（milestone 13 单：#67、#71–#82） |
| 锚点数 | **13**（逐单一个 `[P]` 锚点；锚点 id 与 issue 正文引用逐字一致） |
| 依赖真源 | `docs/discussion/2026-09-08-v1-requirements.md`（各模块 §x.4 `[P]`）；各 issue 正文 `[P]` 行 |
| 不覆盖 | v0.1.3 及更早的反馈验收（见 `docs/playtest/2026-09-08-v013-feedback.md`、`2026-09-08-opening-feedback.md`）；v1.0 后续批次新增单 |
| 与 `[T]` 的边界 | `[T]` = GUT 自动化断言（`bash scripts/verify.sh` 门禁，agent 自验证）；`[P]` = 真人试玩（本文件，人工勾选）。**两者互不替代**：`[T]` 全绿不代表 `[P]` 通过；`[P]` 通过也不豁免 `[T]` |

### 0.3 与 `[T]` 的分工

| 维度 | `[T]`（GUT） | `[P]`（本文件） |
| :--- | :--- | :--- |
| 判定者 | agent（CI/本地 verify） | **真人**试玩者 |
| 判定物 | 断言通过/失败（确定性） | 代理指标实测值 + 玩家原话 |
| 覆盖 | 逻辑正确性、边界、回归 | 可读性、节奏、手感、意愿（"想不想再来一局"） |
| 失败归属 | 代码缺陷 | 设计/呈现缺陷（转 issue） |
| 证据 | `verify.sh` 输出（scripts/tests/asserts） | 截图/录屏 + 试玩记录（§2 模板） |

**纪律**：`[P]` 与 `[T]` 必须**成对**看。例：`#RS-05` 的 `[T] test_saturation_first99_week` 断言"首达 99 分周次 ≥ `benchmarks.json.saturation.first99_week_min`（50）"，而 `[P]` 判的是"玩家看到「已登顶·自由期」时是爽还是懵"——前者绿而后者红，说明护栏在数值上成立、在叙事上失效。

### 0.4 谁来执行

| 角色 | 职责 |
| :--- | :--- |
| **试玩者（人类）** | 按脚本操作、口述感受、勾选 `[P]`；**不得由 agent 代跑** |

| 主程序席 | 构建交付（Release/Pages）、git 与 `verify.sh` 统一处理；裁决附录 C 的阻塞项 |

**画像要求**：每条脚本的判定至少由 **1 名**符合该脚本画像要求的试玩者完成；`#RU-02` 要求 **≥5 名**新玩家样本（需求文档 §9.4 的 `≥80%` 口径）。画像定义见 `.agents/skills/gd-player-persona-review`（开罗老炮 / AI 圈内人 / 移动休闲 / 经营深度）。

## 1. 通用试玩准备

### 1.1 构建来源（三选一，记录必须写明）

| 来源 | 适用 | 取证便利性 | 注意事项 |
| :--- | :--- | :--- | :--- |
| **Release exe**（tag `v0.1.5`） | 桌面全流程、长局（`#RF-02`） | 系统截图/录屏、秒表 | 首选；记录 exe 版本号。**当前状态：v0.1.5 尚无 Release tag**（核对时最新 Release = `v0.1.3`）→ 需主程序席产出后使用（见附录 C-10） |
| **Pages 秒玩**（Web） | 移动端/iPad、快速抽查 | `?shot=` 合成截图 + 信标 | 浏览器缓存会串版本，试玩前强制刷新（Ctrl+Shift+R）；**需主程序席确认当前 Pages 部署的 commit** |
| **本地 main** | 开发中验证 | 编辑器运行 + 控制台 | 必须记录 commit（git 由主程序席执行，试玩者只抄写） |

**对照用基线构建**：`#批0` 需要 v0.1.3 侧构建——**`v0.1.3` Release 已存在**（可下载 exe），可直接作为对照基线使用。

### 1.2 设备与分辨率（含移动端）

| 形态 | 基准 | 必须记录的 | 影响 |
| :--- | :--- | :--- | :--- |
| 桌面横屏 | 1920×1080（窗口 1280×720 亦可） | 分辨率、是否全屏 | 主台四区布局（资源栏 / 周条 / 竞对条 / 工作区） |
| 竖屏 | **375×667** | 视口朝向、折叠后可见元素 | 资源栏副行折叠（研发力 / 技术加成 / 净流入预告）；`#RU-02` 必须含竖屏样本 |

**折叠纪律**（`docs/standards/ui-state-visual-mapping.md` V1-18 行）：副行**保留不折叠**的是净流入预告；折叠的是研发力/技术加成。若试玩发现预告在竖屏被折掉 → 记缺陷（归 `#78`）。

### 1.3 速度档（1x / 2x / 4x）

| 档位 | 每周实际耗时 | 依据 | 用法 |
| :--- | :--- | :--- | :--- |
| 1x | **10s/周** | `src/data/clock.json`：`tick_seconds 0.25` × `ticks_per_week 40` | 需要观察细节、计时类指标（"10 秒内""0.5s 内"） |
| 2x | 5s/周 | 同上 ×2 | 中段快进 |
| 4x | 2.5s/周 | 同上 ×4 | 跨空窗快进（到 W25/W54/W82 等观察点） |

**两个必须写进记录的副作用**：

1. 变速**不改变"周数 → 决策数"映射**（`#RF-02` 的 `[T] test_single_run_duration_guard` 口径），所以快进不会让玩家少做决策，只会让"做决策的时间窗口"变窄；
2. 当前构建**每周结自动弹周报**（z2 阻塞，`dashboard_presenter.gd:236-237`）：4x 下每 2.5 秒弹一次，**会显著打断快进**。试玩时记录"周报打断次数"，并在结论备注中说明它对节奏判断的影响（该结构落差属需求 §9.1 E9-5 既有债，不在 v0.1.5 13 单范围）。

### 1.4 新开局 vs 读档 / 种子

| 项 | 现状（代码实证） | 本文件的规定写法 |
| :--- | :--- | :--- |
| 新开局 | 启动即 `start_new_game(seed=0)`；INTRO 弹层点「开始经营」进入 | ✅ 所有脚本的默认前置 |
| 读档 | **UI 不可达**（`SaveSystem.load_game` 零调用方） | ❌ 禁用"读档到 Wxx"写法；一律写"新开局 + 4x 快进到 Wxx" |
| 种子 | UI 无入口，固定 `seed=0` | 记录里写明"seed=0（UI 固定）"；对照类脚本（`#批0`）因此天然同 seed |
| 存档 | 周结自动存档（`request_save("weekly_auto")`）、破产终局存档 | 只作证据附件，不作前置手段 |

**快进的代价要如实记录**：快进期间的随机事件、竞对发版、自动周报都会发生；若某脚本的观察点被随机事件污染（例如 `#REV-03` 恰好在观察窗内连抽 2 张决策卡），记录者必须标注，并**在结论中区分"设计问题"与"运气"**。

### 1.7 计时与打点方法

1. **计时类指标**（"≤10 秒""0.5s 内"）：从"玩家开始执行该动作"起算到"结果可见"止；用录屏时间戳核对，记录者写下起止帧或秒数。
2. **计数类指标**（"≥3 次""≥5 次""≥8 次"）：由**观察者**记录，不打断玩家；计数时点写进记录（"W12–W40 之间"）。
3. **原话类指标**（"能说出 N 句"）：提问用中性句式（"现在你觉得……？"），**不得提示选项**；`#RF-02` 的三句话（"我封顶了 / 我在守成 / 我想再开一局"）必须由玩家自主说出，试玩者不得复述。
4. **主观估计类**（如"事件贡献 ≤1/3"）：由玩家先给判断，再与实测数据对照；两者不一致时以**实测数据**入表、"玩家判断"入备注。

### 2.1 填写纪律

| 纪律 | 说明 |
| :--- | :--- |
| **原话逐字** | "玩家原话摘录"栏禁止改写、润色、翻译；口音/语气词保留。记录者的解读只能写在"记录者观察"栏 |

### 4.1 `#V1-04` · issue #67 暂停菜单面板缺失

**关联**

### 4.13 `#RF-02` · issue #82 短单局收尾

> 需求文档 §11.4 的 `[P]` 引用锚点为 `#RF-03`，与本节并列声明（同一脚本）。
> **裁决依据**：`docs/discussion/2026-09-08-decision-session-minutes.md` **§十二**（短单局体验：一局 160 周 ≈ 26.7 分钟；W54 封顶 → 三线接管）+ §十四 Q-R3（W160 自动弹 + 可继续自由期；破产与正常终局两套并存；自由期无限延续）。

**关联**

- issue：**#82**（`[0.1.5-3.5] 短单局收尾：自由期三线 + 终局屏 + summary 六项`）
- `[P]` 验收原文（issue 正文逐字）："一局从头玩到尾，玩家能说出「我封顶了 / 我在守成 / 我想再开一局」；**封顶后 17.7 分钟内 ≥3 次三线进度变化**（试玩脚本：docs/playtest/scripts.md#RF-02）"
- 需求模块出处：需求文档 **§11.4** `[P] test_playtest_oneshot_end_to_end`（锚点 `#RF-03`），三段式原文：
  - **步骤脚本**："完整玩完一局（~27 分钟），从开局到终局屏"
  - **预期感受**："**①有高潮**（至少 2 次"想截图"的瞬间）；**②有收尾**（终局屏能说清"我这一局干了什么"）；**③想再开一局**（结束后主动点"重新开局"或讨论"下次我要怎么玩"）"

**前置**

| 项 | 要求 |
| :--- | :--- |
| 构建 | v0.1.5 + **#82 已合并**（PR #99，squash `ffce0f3`；三线计数器 `freedom_*` / 终局屏 / 封顶横幅均已落地） |
| 局面 | 新开局 seed=0，完整玩到 W160（或破产） |

**步骤脚本**

1. 新开局 → 「开始经营」；**1x 全程**（收尾体验依赖真实节奏；快进会破坏"长尾"感受）。
2. 全程记录：两次"想截图"的瞬间（玩家主动说"这个我要截一下"或明显停顿拍照）、封顶周次、竞对压迫点、三线数值变化。
3. 到 W160：观察是否**自动弹**终局屏（非破产专属），核对六项（周数 / SOTA 次数 / 最高分 / 霸榜周数 / 树 n/14 / 影响力存量）+ 关键决策回溯 ≥3 条 + 一句话评价。
4. **不提示**，等玩家自己开口；记录玩家是否自主说出「我封顶了 / 我在守成 / 我想再开一局」。
5. 记录终局后 **≤30 秒**内玩家是否点「重新开局」或明确表达重开意愿。
6. 问玩家（不提示）："下次开一局，你想改哪两个决定？"
7. 统计封顶后（约 17.7 分钟）三线进度变化次数（霸榜周数跳变 / 树 n/14 跳变 / 影响力存量跳变）。

**预期感受**（定性）

**①有高潮**（≥2 次"想截图"）；**②有收尾**（终局屏能说清"我这一局干了什么"）；**③想再开一局**。
