# 0003. 存档升轨迁移链（Schema Migration Chain）

日期：2026-09-07 / 状态：accepted

## 背景

存档是持续迭代最容易崩坏的资产：字段重命名、类型变更、结构重组之后，
旧玩家档案若静默解析失败 = 坏档（玩家进度丢失，不可逆）。
GDScript 无反射，不能像 C# 那样自动迁移；必须在机制上显式保证。

## 决策

1. 存档顶层强制携带 `schema_version: int`（缺失视为 v1）。
2. 迁移逻辑集中在 `SaveMigrator`（纯静态、纯字典操作、可无头单测），
   文件 IO 隔离在 `SaveSystem` autoload。
3. 迁移链逐级升轨（v1→v2→v3…），**禁止跳步合并**——每一步只做最小变更。
4. 未来版本保护：`schema_version` 高于当前代码 → 返回空字典并拒绝加载，
   防止旧版本游戏用旧 schema 覆盖新存档。
5. 每次破坏性 schema 变更：`CURRENT_VERSION` +1，新增一个 match 分支，
   并补对应单测（test_save_migrator.gd）。

## 备选方案

- **每次读档 try/catch 容错**：掩盖问题而非解决，坏档依旧发生。
- **Resource 序列化存档**：加载即实例化，schema 迁移无从下手；且 .tres 有
  Git 合并安全问题，存档文件还会被玩家篡改注入对象。

## 后果

- 正向：任何历史版本存档都能确定性地升到当前 schema；坏档被结构性杜绝；
  迁移逻辑 100% 单测覆盖。
- 代价：每次字段变更都要写迁移步骤（约定成本，远低于坏档事故成本）。
