## 一、版本边界定义

### 1.1 版本序列（人类制作人已裁口径）

```
v0.1.x（已发：v0.1.0 → v0.1.2 → v0.1.3，MVP 切片验证）
  → v0.2（三批：批1 经济+归来感 / 批2 内容+深度 / 批3 二周目+收尾；#26–#45 已裁）
    → v1.0 ＝ MVP 正式发布版（收拢版）
    → v2.0 ＝ MVP 阶段深度演进版（红级解锁版）
```

**1.0 与 2.0 都属 MVP 阶段范畴**（人类制作人已裁决，本提案唯一不可偏离的边界口径）。
原 **v0.3 节点拟取消**【待拍板】，理由见 §1.4。

### 1.2 v1.0 定义：MVP 正式发布版

**一句话**：把 v0.2 三批全部承诺项 + 绿/黄级储备项 + 规格漏译缺口补齐（N1–N8，见 §二.2）收拢进同一个发布里程碑，以"可发布、可玩、好玩"为门槛正式对外。

**发布门槛（门槛件，缺一不发）**：

### 1.3 v2.0 定义：MVP 阶段深度演进版

**一句话**：承载全部红级专项（每项开工前须红级专项评审）+ 周目三件套真身深化 + 等试玩池裁决落地项——是 1.0 发布后由试玩数据驱动的第二波深度，不是新阶段。

**准入规则（三条全过才进 v2.0 排期）**：
1. **红级评审前置**：北岭实体化 / 多竞对同场（DR-029 G-5"红级专项评审"）/ 他者道路互斥竞争态（DR-003 唯一已知升级条件"TechFog 扩态=红（存档迁移），届时专项评审"）——三案各自过一轮红级专项评审（存档迁移链+确定性验收+GDD 同步）后才可立项，未评审不得建 issue；**红级专项评审结论经制作人确认后视同 [change] 双签**（免重复走双签，经对抗评审 m3 明示）；
2. **数据前置（经对抗评审 m4 合并：作为评审输入而非独立门）**：红级专项评审的输入材料必含 v1.0 试玩池真实数据（"第二局值得开"是否成立、三榜是否有可刷目标），无数据不开评审；
3. **等试玩池转正规则**（§三.3）：悬置项按转正规则逐条裁决，转正走 [change] 双签后进 v2.0 首批，不转正即销账留痕（GDD 未决问题）。

### 1.4 v0.3 节点取消【待拍板】

1. **承载已被完全吸收**：排期裁决把储备项标"v0.3+"，隐含定义=红级+真身深化批；现人类已裁"1.0/2.0 都属 MVP 阶段"，绿/黄级储备并入 1.0 收拢、红级归 2.0，v0.3 失去独立内容定义，只剩空壳节点；
2. **纯负担**：每多一个版本节点=一轮完整"排期→冻结→验收→发版"固定开销；对单人+agent 管线，节点切换成本远大于收益；
3. **悬置项不需要版本容器**：等试玩裁决项（气泡停留/摘要条数/gate 三值等）需要的是裁决数据流，随 1.0 试玩池转正即可，不需要独立版本承接；
4. **对外叙事清洁**：0.3 易被误读为"1.0 前还有一次半成品发布"，与"1.0=正式发布版"的传播口径冲突（同 DR-013 命名纪律的逻辑）。

### 1.5 与 DR-016"持续迭代"共识的关系——1.0 不是终点

DR-016 原文共识："MVP 是起点不是终点，v0.1.0 后立即进入数值迭代轮与试玩反馈闭环，持续循环直至发布与长线运营。"本提案对 1.0 的定位是该共识的里程碑化：**1.0 = MVP 阶段"可发布"的正式化时刻，不是项目收尾**。1.0 发布后：试玩反馈闭环（GDD 留痕→分诊→迭代）常设管线不变；数值迭代轮平移为"2.0 演进轮"；等试玩池与四画像画像库持续吸收真实数据（DR-019 演进预留："玩家画像随试玩反馈池持续补充真实画像"）。2.0 亦然——它只是 MVP 阶段内的第二次深度投放，其后仍有持续迭代。
